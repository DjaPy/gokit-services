# SPDD-анализ: Слой метрик для gRPC Server и gRPC Client

## Исходное бизнес-требование

добавить метрики к grpc client и grpc server c учётом текущего состояния кода

---

## Идентификация доменных концепций

### Существующие концепции (из кодовой базы)

- **`server.Server`** (`pkg/grpc/server`): управляемый gRPC-сервер, реализует `service.Service` + `service.Shutdown`. Создаёт `*grpc.Server` внутри `NewServer(opts ...Option)`, экспонирует его через `GRPCServer()`. Опции до правки: `WithHost`, `WithPort`, `WithLogger`, `WithServerOptions`. До этого требования — единственный транспорт без слоя наблюдаемости.

- **`client.Client`** (`pkg/grpc/client`): управляемый gRPC-клиент, реализует `service.Service` + `service.Shutdown`. Соединение устанавливается в `Start`, закрывается в `Stop`. Опции до правки: `WithDialOptions`, `WithLogger`. Также без метрик.

- **Эталон HTTP-инструментации** (`pkg/http/server`): опорный образец. Метрики собираются middleware-обёрткой (`buildMiddleware` + `responseWriter`), семейства `http_request_duration_seconds`, `http_response_size_bytes`, `http_requests_inflight`, `http_panic_recovery_total`; label-таксономия `http_service`(=appName) / `http_handler` / `http_method` / `http_code`; конфигурация через `WithAppName` и `WithPrometheusRegisterer`; `initMetrics()` вызывается в конструкторе.

- **Эталон не-HTTP инструментации** (`pkg/kafka/producer`, `pkg/kafka/consumer`, `pkg/dbservice`, `pkg/redisservice`): подтверждает сквозную конвенцию — label вида `<protocol>_service`(=appName), собственный `initMetrics()`, пары counter+error counter+duration histogram, регистрация через общий helper.

- **`internal/prom.RegisterOrReuse`** (`pkg/internal/prom`): общий идемпотентный helper регистрации коллектора — при повторной регистрации того же коллектора возвращает существующий вместо паники. Именно он снимает старое ограничение «второй `NewServer` на дефолтном registerer паникует» и позволяет создавать несколько экземпляров на `DefaultRegisterer`.

- **`prometheus.Registerer` / `prometheus.DefaultRegisterer`**: сквозная конвенция — по умолчанию дефолтный registerer в проде, изолированный `prometheus.NewRegistry()` в тестах.

- **gRPC interceptors** (`UnaryServerInterceptor`, `StreamServerInterceptor`, `UnaryClientInterceptor`, `StreamClientInterceptor` из `google.golang.org/grpc v1.81.1`): транспортно-нативная точка расширения — прямой аналог HTTP-middleware, но с явным разделением на unary и stream. Уже частично упомянуты в docstring `WithServerOptions`/`WithDialOptions` как способ пробросить interceptor'ы снаружи.

### Новые концепции, которые нужно добавить

- **Контракт наблюдаемости gRPC**: семейства метрик `grpc_server_*` (сервер) и `grpc_client_*` (клиент) — зеркало `http_*`, но с новой размерностью потоковости. Это часть публичного контракта библиотеки (потребители строят по ним алерты/дашборды), поэтому нейминг и набор label'ов — доменное решение, а не деталь реализации.

- **Размерность `grpc_type`** (`unary` / `client_stream` / `server_stream` / `bidi_stream`): новая ось, отсутствующая в HTTP-модели (у HTTP нет типов стрима). Определяет семантику того, как считается длительность и inflight.

- **Слой interceptor-инструментации для обоих концов**: встроенный в `NewServer`/`NewClient`, аналог `http/server buildMiddleware`, но раздвоенный на unary+stream и на серверную/клиентскую стороны.

- **Наблюдение жизненного цикла стрима на клиенте**: клиентский стрим переживает вызов interceptor'а (interceptor лишь открывает поток) — чтобы узнать терминальный статус и полную длительность, нужна обёртка над `ClientStream`, фиксирующая завершение. Концепции-аналога в HTTP нет.

- **Единообразные опции конфигурации для gRPC-пары**: `WithAppName` и `WithPrometheusRegisterer` в обоих пакетах — восстанавливают симметрию с `http/server` и инфраструктурными сервисами.

### Ключевые бизнес-правила

- **Единообразие с существующей инструментацией**: gRPC-метрики обязаны следовать той же конвенции опций (`WithAppName`/`WithPrometheusRegisterer`) и label-таксономии (`<protocol>_service` = appName), что и `http/server`, `kafka/*`, `dbservice`, `redisservice`. Управляет неймингом метрик и сигнатурой опций.
- **Сосуществование с пользовательскими interceptor'ами**: встроенные метрики не должны затирать interceptor'ы, переданные через `WithServerOptions`/`WithDialOptions`, а должны их оборачивать (chaining). Управляет способом регистрации interceptor'а.
- **Метрики включены по умолчанию, но безопасны**: как у `http/server`, инструментация активна без явного включения; `appName` по умолчанию пуст. Управляет поведением «из коробки».
- **Инвариант баланса inflight**: gauge «in-flight» обязан сходиться к нулю после завершения RPC (каждому `Inc` соответствует `Dec`). Управляет корректностью серверной и клиентской реализации.
- **Безопасность повторного создания**: несколько `NewServer`/`NewClient` на одном registerer не должны паниковать — обеспечивается `RegisterOrReuse`, но требует идентичного набора label'ов между экземплярами. Управляет использованием общего helper'а.
- **Библиотека — переиспользуемый тулкит без тегов версий**: изменение публичного API (новые экспортируемые опции, новый контракт метрик) для `v0.x` допустимо в MINOR, но контракт метрик становится тем, на что закладываются потребители. Управляет тем, что нейминг метрик стоит зафиксировать сразу правильно.

## Стратегический подход

### Направление решения

Инструментировать оба пакета через gRPC-interceptor'ы (отдельно unary и stream), встроенные в конструкторы `NewServer`/`NewClient` — по прямой аналогии с middleware-слоем `http/server`. Переиспользовать `internal/prom.RegisterOrReuse` и конвенцию `prometheus.Registerer`; добавить в оба пакета `WithAppName` и `WithPrometheusRegisterer`. Ввести контракт метрик `grpc_server_*` / `grpc_client_*` с label-таксономией `grpc_service`(=appName) / `grpc_type` / `grpc_method` / `grpc_code`, зеркалящей `http_*`. Поток данных: `gRPC RPC → встроенный interceptor (замер времени/кода/inflight) → пользовательский handler/invoker`, метрики пишутся в общий registerer, экспонируются существующим `healthserver`/`/metrics` без изменений.

### Ключевые решения дизайна

- **Способ подключения interceptor'а: chaining (outermost) vs единичный interceptor.**
  gRPC допускает только один `UnaryInterceptor`/`StreamInterceptor` (последний затирает предыдущий), но `ChainUnary/StreamInterceptor` аккумулируются.
  → **Рекомендация**: регистрировать метрический interceptor через `ChainUnary/StreamInterceptor`, **добавляя его первым (внешним)** к тем, что пришли через `WithServerOptions`/`WithDialOptions`. Иначе встроенные метрики либо затрут пользовательские interceptor'ы, либо не измерят их вклад. Трейд-офф: порядок регистрации становится значимым инвариантом.

- **Label-таксономия: `grpc_service`=appName + полный метод в одном label `grpc_method` vs раздельные label'ы proto-сервис/метод (стиль go-grpc-prometheus).**
  → **Рекомендация**: `grpc_service`=appName (зеркало `http_service`), полный метод RPC — в один label `grpc_method` (зеркало `http_handler`). Так gRPC-метрики читаются одинаково с HTTP. Трейд-офф: нельзя из коробки агрегировать по proto-сервису отдельно от метода, но это компенсируется PromQL по префиксу `grpc_method`.

- **Семантика длительности стрима: серверный стрим vs клиентский.**
  Серверный handler блокируется на всё время стрима, поэтому его замер даёт полную длительность естественным образом. Клиентский `streamer()` возвращается сразу, стрим живёт дальше.
  → **Рекомендация**: сервер — мерить время жизни handler'а без обёртки; клиент — обернуть `ClientStream` и фиксировать метрику при завершении стрима (терминальный `RecvMsg`: `io.EOF` → `OK`, иначе статус-код). Трейд-офф: если потребитель не дочитывает клиентский стрим до конца, метрика завершения не сработает (см. риски).

- **Где инициализировать метрики: в конструкторе vs в `Start`.**
  Kafka-продюсер инициализирует метрики в `Start` (после коннекта), `http/server` — в конструкторе.
  → **Рекомендация**: в конструкторе (`NewServer`/`NewClient`), как `http/server` — потому что interceptor'ы должны захватить готовые метрик-вектора в момент сборки `*grpc.Server`/`dialOpts`. Трейд-офф: коллекторы регистрируются уже при создании объекта, до `Start` (совпадает с поведением `http/server`).

- **Источник значения `grpc_code`.**
  → **Рекомендация**: канонические имена статусов gRPC (`status.Code(err).String()` → `OK`, `Canceled`, `NotFound`, …) — читаемо и стандартно для gRPC-дашбордов.

### Рассмотренные альтернативы

- **Внешняя библиотека `go-grpc-middleware/providers/prometheus` (grpcprom)**: даёт готовые interceptor'ы и метрики, но (а) добавляет внешнюю прод-зависимость, (б) её label-таксономия (`grpc_service` = proto-сервис) расходится с конвенцией репозитория (`<protocol>_service` = appName), (в) проект последовательно реализует инструментацию сам (http/kafka/db/redis — всё ручное, на общем `RegisterOrReuse`). Отклонено ради единообразия и нулевых новых прод-зависимостей.
- **OpenTelemetry / `otelgrpc`**: другой стек наблюдаемости (traces+metrics через OTLP), не Prometheus-first. Несовместимо с текущей моделью (`prometheus.Registerer`, экспозиция через `healthserver`). Выходит за рамки требования — отклонено.
- **Инструментировать только сервер, клиент оставить как есть**: требование явно называет оба конца; асимметрия наблюдаемости недопустима. Отклонено.
- **Мерить клиентский стрим только в момент открытия (без обёртки `ClientStream`)**: проще, но даёт неверную длительность (микросекунды на открытие потока) и теряет терминальный код. Отклонено ради корректности.

## Анализ рисков и пробелов

### Неоднозначности требования

- **Набор метрик не зафиксирован**: требование не говорит, что именно мерить (только latency? счётчики завершений? in-flight? размер сообщений?). Принято зеркалить HTTP-набор — histogram длительности + counter завершений (с `grpc_code`) + gauge in-flight. Нужно подтверждение достаточности.
- **Label-таксономия не задана**: `grpc_service`=appName и единый `grpc_method` — это решение по аналогии, а не факт из требования. Требует подтверждения.
- **Формулировка «с учётом текущего состояния кода» двусмысленна**: (а) следовать текущим конвенциям инструментации (http/kafka), (б) учесть уже присутствующие в коде наработки. Принято сочетание: опираться на конвенции эталонных пакетов и не ломать существующий публичный API gRPC-пары.
- **Размер сообщений (bytes)**: у HTTP есть `http_response_size_bytes`; прямого дешёвого аналога в gRPC нет без инспекции payload. Исключено из объёма — требует подтверждения, что это не нужно.

### Граничные случаи

- **Недочитанный клиентский стрим (`client_stream`/`bidi_stream`)**: если потребитель не доводит `RecvMsg` до `io.EOF`/ошибки (бросает стрим, отменяет контекст и не читает), обёртка не зафиксирует завершение → метрика завершения не запишется, а gauge in-flight «протечёт» (не декрементируется). Это известное ограничение подхода (то же у go-grpc-prometheus) — нужно осознанно принять и задокументировать.
- **Паника в gRPC-handler'е**: у gRPC (в отличие от `http/server`, который ловит панику и пишет `http_panic_recovery_total`) нет встроенного recovery — паника обрушит обработку; метрический interceptor без явного `recover` статус-код не зафиксирует корректно. Требование про метрики, не про recovery, поэтому panic-recovery для gRPC — вне объёма, но пробел стоит явно отметить (возможный будущий `grpc_panic_recovery_total`).
- **Несколько экземпляров на общем registerer**: `RegisterOrReuse` переиспользует коллектор только при идентичном наборе label'ов; если серверный и клиентский (или два серверных) наборы label'ов когда-либо разойдутся под одним именем метрики — будет паника. Инвариант «одно имя метрики — один набор label'ов» надо соблюдать.
- **Пустой `appName` по умолчанию** → `grpc_service=""`. Совпадает с поведением `http/server`, но снижает читаемость на дашбордах при нескольких сервисах в одном namespace.
- **Кардинальность `grpc_method`**: ограничена числом зарегистрированных RPC (в отличие от свободных HTTP-path), поэтому приемлема; отдельного контроля не требует.

### Технические риски

- **Семантика chaining-порядка**: несколько `ChainUnary/StreamInterceptor` аккумулируются в порядке добавления; корректность длительности зависит от того, что метрический interceptor — внешний. Риск регресса при будущих правках порядка сборки опций. Митигация: тест, проверяющий, что пользовательский interceptor всё ещё вызывается и учитывается.
- **Протечка in-flight gauge на стримах** (см. граничные случаи): риск для целостности данных наблюдаемости. Митигация: документировать контракт «дочитывайте стрим до конца» либо декрементировать также по завершению контекста стрима.
- **`go.mod` direct/indirect**: тестовая проверка метрик на реальных RPC требует стандартного gRPC health-сервиса и модели метрик Prometheus, что может перевести `client_model` в прямые зависимости — нужен `go mod tidy` в рамках реализации.
- **Регистрация коллекторов в конструкторе**: создание `Client`/`Server` без `Start` уже регистрирует метрики в registerer. Совпадает с `http/server`, но это осознанный сдвиг относительно kafka-подхода (регистрация в `Start`) — стоит принять как согласованное с HTTP-эталоном.
